# Build and Distribution

Everything in this document exists to turn a TypeScript workspace into one
self-contained executable sitting on somebody's `PATH`, and then to keep that
executable current without anyone thinking about it.

There is no package to install, no runtime to provision, and no `node_modules`
on the target machine. `bun build --compile` produces a single file — 65 MB for
darwin-arm64, 101 MB for linux-x64 at 1.1.0 — that embeds the Bun runtime
alongside the bundled source, and that file is the whole product. Every design decision below follows from that: the version has to be
baked in at compile time because there is no `package.json` to read at runtime,
the upgrade path has to replace a running binary in place, and the installer has
to be a shell script because nothing else is guaranteed to exist on a fresh host.

## The workspace

The repository root is `home-monorepo`, private, with `packageManager` pinned to
`bun@1.3.14` and workspaces `apps/*` and `packages/*` (`package.json:2-8`). Three
members exist:

| Workspace | Package | What it is |
| --- | --- | --- |
| `apps/home` | `home` | The CLI — source, tests, build scripts, the thing that ships |
| `apps/site` | `@home/site` | `home.uptonm.dev` |
| `packages/brand` | `@home/brand` | Image assets, no code |

`packages/brand` declares no scripts at all — it is a `files` and `exports` map
over a directory of PNGs and one SVG (`packages/brand/package.json:5-20`). Its
assets are regenerated by `packages/brand/build.py`, a Python script run by hand
against a hardcoded macOS system font path; nothing in the build or CI touches
it.

Root scripts are thin `bun run --cwd` delegations, namespaced by workspace, plus
four aggregates — `typecheck`, `test`, `build`, and `ci` (`package.json:9-24`).
`bun.lock` at the root is the only lockfile.

The site is out of scope here; it is described in
[`004-DOCUMENTATION-PUBLISHING`](./004-DOCUMENTATION-PUBLISHING.md).

## Bun is four tools; Biome is one, and only on the site

Bun's four roles are each verifiable in configuration rather than by convention:

- **Runtime.** `apps/home` requires `bun >= 1.3.0` (`apps/home/package.json:7-9`)
  and its `bin.home` entry points at `./src/index.ts` — a TypeScript file used
  directly as an executable, which only works because Bun runs TypeScript without
  a build step (`apps/home/package.json:10-12`).
- **Package manager.** One `bun.lock`, `bun install --frozen-lockfile` in both
  workflows (`.github/workflows/ci.yml:17`,
  `.github/workflows/release-please.yml:51`).
- **Test runner.** `apps/home/bunfig.toml` configures `[test] preload`, and every
  suite imports from `bun:test`.
- **Bundler.** `bun build --compile` is the only bundler invoked anywhere.

Typechecking is the one job Bun does not do: both workspaces run `tsc --noEmit`
(`apps/home/package.json:15`, `apps/site/package.json:12`).

Biome's scope is narrower than the monorepo. `apps/site/biome.json` is the only
Biome configuration, `@biomejs/biome` 2.2.0 is a devDependency of `@home/site`
alone (`apps/site/package.json:35`), and `lint` and `format` scripts exist only
there (`apps/site/package.json:13-14`). `apps/home` declares neither, so the
CLI — the larger of the two by a wide margin — is not linted or formatted by any
tool. Its style is held by review.

## Tests run one process per file, and that is not an optimization to undo

`bun run test` is `bash scripts/test-isolated.sh`, never `bun test`. The reason
is written at the top of the script (`apps/home/scripts/test-isolated.sh:3-14`):
Bun's `mock.module()` is process-global with no teardown, and Bun evaluates every
test file's module scope before running any test, so a file that mocks a client
module replaces it for the file whose entire purpose is exercising the real one.
`--isolate` and `--parallel` do not help — they break top-level-await imports in
the sonos suites instead. Every file passes alone, so every file gets its own
process, at a cost of about a second.

Flags are rejected rather than forwarded (`apps/home/scripts/test-isolated.sh:21-23,31-40`),
because `bun test --coverage` — or any flag — would collapse the run back into
one process and reintroduce precisely the leakage the script exists to prevent.
A single file argument execs `bun test <file>` directly (`:41-43`). Discovery
reimplements Bun's own patterns, `.test`/`_test`/`.spec`/`_spec` across four
extensions, so a file Bun would run can never be silently skipped, and avoids
`mapfile` because macOS still ships bash 3.2 (`:46-59`). The script runs under
`set -uo pipefail` without `-e` so one failing file does not abort the sweep;
failures are collected, re-run, and reported with their last 30 lines (`:67-83`).

`bun run e2e` is a separate entrypoint that drives the dev CLI against the real
homelab, and is the pre-release gate rather than part of `bun test`. Its
presentation is covered in
[`000-CLI-OUTPUT-CONTRACT`](./000-CLI-OUTPUT-CONTRACT.md).

## `build` writes to `dist/`; only `build:install` touches your `PATH`

Both compile through the same script. The only difference is the first argument:

```
build          bash scripts/build-local.sh                    → apps/home/dist/home
build:install  bash scripts/build-local.sh $HOME/.local/bin/home → ~/.local/bin/home
```

`apps/home/scripts/build-local.sh:8` defaults the output to `dist/home`, which is
gitignored (`.gitignore:3-4`), so `bun run build` cannot affect anything outside
the repository. `bun run build:install` (`apps/home/package.json:18`) writes
straight over the binary on `PATH`. There is no confirmation prompt, no version
comparison against the installed binary, and no requirement that the working tree
be committed — **`build:install` will install a `-dirty` build from uncommitted
work without comment**, which is exactly what makes it useful during development
and exactly what makes it dangerous afterwards.

The build stamps the tree state it saw: the short `HEAD`, suffixed `-dirty` when
`git diff --quiet` reports modifications (`apps/home/scripts/build-local.sh:34-35`).
That suffix is load-bearing downstream — a `-dirty` binary suppresses the update
banner entirely (`apps/home/src/core/update.ts:173-174`), on the reasoning that a
build ahead of the latest release should not be told it is behind.

Target selection maps `uname` to a Bun target across four hosts, defaulting Linux
x86_64 to `bun-linux-x64-baseline` so the binary does not require AVX
(`apps/home/scripts/build-local.sh:23-31`). `HOME_BUILD_TARGET` overrides it
(`:9`), which makes `build-local.sh` a cross-compiler as well as a host builder.
The script also re-derives `PATH` candidates for `bun` so it works from a
non-interactive shell (`:12-21`).

On macOS the output is codesigned with a local "Home CLI Dev" identity when one
exists (`apps/home/scripts/build-local.sh:49-56`). The probe is
`security find-certificate` rather than `find-identity -v`, because the latter
excludes self-signed certificates for lacking trust while `codesign` will happily
use them anyway. `apps/home/scripts/setup-codesign.sh` creates that identity once
per machine: a ten-year self-signed code-signing certificate imported into the
login keychain with `-T /usr/bin/codesign`, followed by a partition-list repair so
`codesign` can use the key without a GUI dialog per build. What it explicitly does
not do is stop macOS re-asking for keychain access after a rebuild — the ACL pins
the grant to the binary's cdhash, not to its signing identity, so new bytes always
re-ask (`apps/home/scripts/setup-codesign.sh:7-16`).

## `build:linux` and `build:mac` bypass the script, and lose the stamp

`bun run build:linux` and `bun run build:mac`
(`apps/home/package.json:19-20`) call `bun build --compile` directly with a fixed
`--target` and an outfile name matching the corresponding release asset. They do
not go through `build-local.sh`, and therefore pass no `--define`.

That omission is not cosmetic. `IS_PACKAGED` is literally
`typeof __HOME_VERSION !== 'undefined'` (`apps/home/src/core/version.ts:34`), so a
binary produced by these two scripts is indistinguishable from source at runtime:
`home upgrade` refuses it with `not_packaged` (`apps/home/src/commands/upgrade.ts:25-36`),
the update preflight returns immediately (`apps/home/src/core/update.ts:174`), and
`--version` falls through to `devVersion()` and `devCommit()`
(`apps/home/src/core/version.ts:4-23`) — the latter shelling out to
`git rev-parse --short HEAD` in whatever directory the user happens to be standing
in, or reporting `dev` when that fails.

`HOME_BUILD_TARGET=bun-darwin-arm64 bun run build` produces the same
cross-compiled binary with the defines intact.

## Version and commit are compile-time constants

`apps/home/src/core/version.ts` declares two globals that exist only if the
bundler substituted them (`:1-2`), resolves each to either the define or a
development fallback (`:25-26`), and exports `IS_PACKAGED` as the presence test
(`:28-34`). Nothing reads a `package.json` at runtime in a real binary, because
there is none to read.

`apps/home/src/index.ts:26-27` composes the display string once: bare
`HOME_VERSION` normally, `HOME_VERSION (HOME_COMMIT)` when `--verbose` appears
anywhere in argv. `--version` (or `-v`) writes that string to stdout and exits 0
at `:29-32`, before the command tree is constructed and before the preflight
runs — so `home --version` is the shortest path through the binary and can never
print an update banner. The same string becomes citty's root `meta.version`
(`:41`), so `--help` shows it too.

`-v` is version, not verbose. `--verbose` is a global flag on every leaf command
per [`000-CLI-OUTPUT-CONTRACT`](./000-CLI-OUTPUT-CONTRACT.md); at the root it
only decorates the version string.

## The update banner is read from a cache and never blocks

`preflight(process.argv)` runs for every invocation except `upgrade`
(`apps/home/src/index.ts:35`). It is wrapped in a bare `try`/`catch` that swallows
everything (`apps/home/src/core/update.ts:171-196`), on the principle that a
broken update check must not break the command someone actually ran.

Six conditions suppress the banner, checked in order: the binary is not packaged,
its commit is `-dirty` or `dev`, stderr is not a TTY, `--json` is in argv, `CI` is
set in the environment, or `updateCheck` is `false` in the global config
(`apps/home/src/core/config.ts:16-17`). That last switch is settable only by
editing `~/.config/home/config.json` by hand — `home config` exposes just `export`
and `import` (`apps/home/src/commands/config.ts:73-86`). The banner itself goes to
stderr (`apps/home/src/core/update.ts:191`), as the output contract requires.

The decision is factored into `bannerFor`, a pure function over a `BannerEnv`
record (`apps/home/src/core/update.ts:143-147`), so the whole suppression matrix
is unit-testable without a filesystem, a TTY, or a network. The call site rechecks
each condition inline and then passes literals for all six (`:181-190`), so at
runtime only the cache-and-compare branch of it is live.

Nothing about this path touches the network. The banner is rendered from
`$XDG_CONFIG_HOME/home/update-check.json` (`apps/home/src/core/paths.ts:34-36`),
and when that cache is older than the 24 hour TTL
(`apps/home/src/core/update.ts:13`) the process detaches a child
running `process.execPath __update-check` with all three stdio streams ignored and
`unref()`s it (`:149-163`). The current command exits immediately; the refresh
benefits the *next* run. `apps/home/src/index.ts:19-22` handles `__update-check`
as the very first statement in the program, before the module registry is walked
and before any preflight, so the child stays silent and cannot recurse. Cache
writes go through a `.partial` file and a rename, and swallow every error (`:57-68`).

The module and command tree the rest of `index.ts` assembles is described in
[`005-MODULE-SYSTEM`](./005-MODULE-SYSTEM.md).

## `home upgrade` verifies the new binary before it swaps

`apps/home/src/commands/upgrade.ts` takes `--check`, `--yes`, and `--tag` (`:7-12`)
and refuses in a fixed order: not packaged (`:25-36`), unsupported platform
(`:38-50`), latest version unresolvable (`:52-59`), `--check` short-circuits with
`{current, latest, updateAvailable}` (`:63-66`), already current without an
explicit `--tag` (`:69-72`), and finally missing `--yes` (`:74-86`). That last one
is the house rule stated in the code: a binary-mutating action never prompts, it
demands a flag.

`currentTarget()` maps platform and arch to the asset name `home-<os>-<arch>` and
returns null for anything other than linux-x64 and darwin-arm64
(`apps/home/src/core/self-install.ts:22-29`), with a comment naming the release
workflow's matrix as the thing it must stay in sync with. The download is
`gh release download --repo uptonm/home --pattern <asset> --clobber` with a 120
second timeout (`:40-61`); `gh` is resolved by `ghBinary()`
(`apps/home/src/core/update.ts:76-84`), which prefers the `github` module's
configured `binaryPath` before falling back to `gh` on `PATH`, so the upgrade path
inherits that module's configuration.

`performUpgrade` (`apps/home/src/core/self-install.ts:99-143`) is the careful part:

1. Stage into the install directory when it is writable, otherwise into `tmpdir`
   (`:100-102`) — staging beside the target is what makes the swap a rename rather
   than a copy across filesystems.
2. `chmod 755`, and on darwin re-sign ad-hoc so Gatekeeper accepts a file that
   arrived over the network (`:105-110`).
3. **Run the staged binary with `--version` and abort if it exits non-zero**
   (`:112-116`). A corrupt or wrong-architecture download is discovered while the
   working `home` is still in place.
4. Swap by renaming the current binary to `.home.bak`, renaming the new one in,
   and rolling the backup back if that second rename fails (`:118-128`). Where the
   directory is not writable, fall back to `sudo mv` and surface
   `upgrade_permission_denied` if it fails (`:129-140`).

On success the command writes the update cache itself
(`apps/home/src/commands/upgrade.ts:91`) so the banner clears on the next run
rather than 24 hours later.

Because the upgrade targets `dirname(process.execPath)` and the installer defaults
to `~/.local/bin`, the same path `build:install` writes, all three routes converge
on one file. Nothing arbitrates between them: `home upgrade --yes` on a locally
built binary replaces it with the release, and there is no dirty check on that
path to stop it.

## release-please cuts the release; the same run builds the binaries

`release-please-config.json` declares exactly one package — `apps/home`, release
type `node`, package name `home` — and `.release-please-manifest.json` pins it at
`1.1.0`, matching `apps/home/package.json:3`. The package name becomes the tag
component, so releases are tagged `home-vX.Y.Z`.

`.github/workflows/release-please.yml` runs on every push to `main`. The first job
maintains a rolling release PR from conventional commits and exports
`apps/home--release_created`, `--tag_name`, and `--version` (`:15-23`); merging
that PR bumps `apps/home/package.json` and `apps/home/CHANGELOG.md`, pushes the
tag, and creates the GitHub Release.

The `publish` job is conditional on `release_created` and lives in the same
workflow run for a specific reason recorded at `:25-28`: the default `GITHUB_TOKEN`
release-please pushes the tag with deliberately does not trigger tag-triggered
workflows, so a separate on-tag workflow would simply never fire. It builds a
two-entry matrix — `ubuntu-latest`/`bun-linux-x64-baseline`/`home-linux-x64` and
`macos-14`/`bun-darwin-arm64`/`home-darwin-arm64` (`:34-42`) — checks out the tag,
and compiles with `--define __HOME_VERSION` and `__HOME_COMMIT` written inline
(`:52-60`). That is a third, independent copy of the define logic, alongside
`build-local.sh` and the two cross-compile scripts. Assets go up with
`gh release upload --clobber`, and the linux leg additionally uploads
`scripts/install.sh` (`:61-69`).

CI itself (`.github/workflows/ci.yml`) runs typecheck, the isolated test sweep,
`site:lint`, and `site:build` on every pull request under Bun 1.3.14 (`:13-23`).
It does not compile the CLI — `bun run build` is never invoked on a pull request —
so the first `bun build --compile` of any change happens in the release job, after
the tag exists. The four steps duplicate the root `ci` script
(`package.json:23`) rather than calling it.

## The installer is one file with two front doors

`scripts/install.sh` at the repository root is the single source of truth. It is
reachable at the raw GitHub URL on `main` and at `home.uptonm.dev/install.sh`;
how the site serves that short URL belongs to
[`004-DOCUMENTATION-PUBLISHING`](./004-DOCUMENTATION-PUBLISHING.md), and the
command itself is defined once for the site at
`apps/site/src/lib/site-config.ts:10`.

The script defaults `HOME_REPO` to `uptonm/home` and the version to `latest`
(`scripts/install.sh:8-9`). `detect_target` maps `uname` to `home-<os>-<arch>` and
refuses anything but linux-x64 and darwin-arm64 with a message naming the missing
combination (`:11-30`). `download_asset` tries the plain
`releases/latest/download/<asset>` URL with `curl` first, precisely so a fresh host
needs no `gh`, and falls back to `gh release download` only when curl fails and
`gh` is authenticated (`:32-56`). `pick_install_dir` prefers `~/.local/bin` when it
is already on `PATH`; when it is not, it offers `/usr/local/bin` with sudo — but
only when stdin is a TTY, and defaults back to `~/.local/bin` either way
(`:58-70`). It then downloads to a temp file, `chmod +x`, moves it into place, and
prints `home init` as the next step (`:72-88`). Regenerating the agent skills after
an install is a separate step, described in
[`009-SKILL-GENERATION`](./009-SKILL-GENERATION.md).

The installer performs no equivalent of `performUpgrade`'s launch check — the
downloaded file is made executable and moved without ever being run.

## Known drift

**The release tag format defeats the update check.** `parseLatestTag` accepts a
`tagName` only if it matches `/^\d+\.\d+\.\d+/` after `normalizeVersion` strips a
single leading `v` (`apps/home/src/core/update.ts:24-26,86-94`). release-please
tags this package `home-vX.Y.Z`, and the two most recent releases on the remote
are `home-v1.0.0` and `home-v1.1.0`. `normalizeVersion('home-v1.1.0')` returns the
string unchanged, the regex rejects it, and `fetchLatestVersion` returns null.
Consequently the update cache is never written and the banner cannot appear;
`home doctor` always reports `updateError` (`apps/home/src/commands/doctor.ts:30,36`);
and `home upgrade` without `--tag` fails with `latest_unavailable`. The unit test
covering the parser feeds `{"tagName":"v0.2.0"}`
(`apps/home/src/__tests__/update.test.ts:109`), a shape the release automation does
not produce.

**`--tag` uses the same wrong namespace.** `apps/home/src/commands/upgrade.ts:23`
normalizes the flag to a leading `v` and passes `vX.Y.Z` to `gh release download`.
Only `v0.1.0`, which predates the current scheme, exists under that name.

**Two comments call the repository private.** `apps/home/src/core/update.ts:10` and
`apps/home/src/core/self-install.ts:41-42` both justify the hard dependency on `gh`
by saying the release repo is only reachable through its auth. `uptonm/home` is
public, as `scripts/install.sh:32-34` and `apps/home/README.md:67-68` both already
state — which is why the installer prefers plain `curl`. `home upgrade` still
requires `gh` on the strength of a stale comment.

**`git diff --quiet` misses staged and untracked work.**
`apps/home/scripts/build-local.sh:35` compares the working tree to the index, so
running `git add` before `bun run build:install` produces a binary stamped with a
clean commit whose tree it does not match — and, because the `-dirty` suffix is
what suppresses the update banner, one that will also start nagging about a
release it is ahead of.

**`build-local.sh` shells out to `node`.** Line 33 reads the version with
`node -e "console.log(require(...).version)"`. Node is declared nowhere in the
repository; the same script goes to considerable trouble to locate `bun` when
`PATH` is thin (`:12-21`) and then assumes a second runtime unconditionally.

**`setup-codesign.sh` points at scripts that do not sign.** Its closing message
tells the user to run `bun run build:mac` or `bun run build:linux` and the binary
will be signed (`apps/home/scripts/setup-codesign.sh:87`). Neither script
codesigns; only `build-local.sh` does, and neither is `build:mac` nor
`build:linux` routed through it.

**`apps/home/README.md` documents the wrong build commands.** Its Development
section lists `build:linux` and `build:mac` as the way to build
(`apps/home/README.md:792-793`) without mentioning `build` or `build:install`, and
its Updating section says the release "tags `vX.Y.Z`" (`:74`).

**The preflight's `upgrade` exemption is positional.**
`apps/home/src/index.ts:35` tests `process.argv[2] !== 'upgrade'`, so
`home --verbose upgrade` still prints a banner directly above a command whose
entire job is reporting version state.

**A published environment variable does nothing.** `scripts/install.sh:5`
documents `HOME_VERSION=v0.1.0`; the code reads `HOME_VERSION_TAG` (`:9`).

**Two release artifacts have no consumer.** The `install.sh` uploaded to each
release (`.github/workflows/release-please.yml:65-69`) is never fetched from there
— both documented entry points resolve to `main`, so the served installer is
always tip-of-main rather than the latest release. And `apps/home/package.json:10-12`
declares a `bin` entry in a package marked `private`, which nothing installs.
